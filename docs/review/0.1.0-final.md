# Last review before release 0.1.0

Live adversarial review on 2026-10-31, at commit `86c8ffd`, on the pinned versions: Metabase `v0.65.2.3`, Cube `v1.8.15`, ClickHouse `26.8.36-alpine`. The stack ran in compose project `mcd-review` on `nettop.local`, from a new clone. It had Cube with the ClickHouse dialect and stock Cube, side by side. The truth is direct SQL on the ClickHouse of that project. I wrote the query list before I read `docs/review/0.1.0.md`.

The scripts are in `dev/review/`. `dev/review/run_all.sh` runs all of it from zero. The outputs are in `dev/review/results/`, and each result that is not a pass is in `results/*.notpass.txt`. Each finding below has its repro in `results/evidence.log`, from `dev/review/evidence.py`.

## Result

**Do not release yet: 4 blockers.** With a UTC report time zone, most shapes give the truth. The defects are in shapes that the suite does not try. The worst group needs only a report time zone that is not UTC.

| Severity | Count | Findings |
| --- | --- | --- |
| Blocker | 4 | B1 to B4 (B4 has three parts) |
| Major | 4 | M1 to M4 |
| Minor | 5 | m1 to m5 |

A blocker is a wrong number with no error that the driver can stop, a leaked secret, a permission bypass, an effect on another database, or a broken install. All 4 blockers are wrong numbers. The other four kinds did not occur.

## Blockers

### B1: an equal filter on a time returns the whole bucket

If `x = T` is next to a breakout on `x`, and `T` is the start of a bucket, Cube returns the whole bucket. The row at `T` is not what counts. This happens in `/api/dataset` and MCP, on both variants of Cube, on tables and views. A Metabase person gets this shape from the API or an agent. A filter from the date picker has a day unit, and it gives the truth.

| Query | Output | Truth |
| --- | --- | --- |
| `orders.count` by month, `created_at = 2025-03-01T00:00:00` | `434` | no rows |
| `orders.count` by year, `created_at = 2025-01-01T00:00:00` | `5000` | no rows |
| `big_orders.count` by hour, `created_at = 2024-03-15T02:00:00` | `600` | `1` |
| `typed_events.count` by quarter, `ts_utc = 2025-04-01T00:00:00` | `257` | `1` |

Command: `python3 dev/review/evidence.py`. The SQL is:

```sql
SELECT DATE_TRUNC('month', "orders"."created_at") AS "created_at", MEASURE("orders"."count") AS "sum" FROM "orders"
WHERE "orders"."created_at" = TIMESTAMP '2025-03-01 00:00:00' GROUP BY DATE_TRUNC('month', "orders"."created_at") ORDER BY DATE_TRUNC('month', "orders"."created_at") ASC
```

The driver can stop this. It sees the filter and the breakout. `x >= T AND x <= T` gives the truth in the same query. Native SQL has the same result, so the scan needs this shape too. 30 shapes in the grid show it: `core/*/first_second` and `follow/eq/*`.

### B2: a case-sensitive text filter ignores case

`contains`, `starts-with`, `ends-with` and `does-not-contain` are case sensitive in Metabase by default. On Cube they ignore case. The filter widgets of the UI send `case-sensitive: false`, so they are not affected. MBQL through the API, MCP and native `LIKE` are.

| Query | Output | Truth, and Metabase on Postgres with the same data |
| --- | --- | --- |
| `orders.count`, `status contains "COMP"` | `2000` | `0` |
| `orders.count`, `status does-not-contain "COMP"` | `3000` | `5000` |
| `users.count`, `name contains "USER 1"` | `111` | `0` |
| Native `SELECT MEASURE(count) FROM orders WHERE status LIKE '%COMP%'` | `2000` | `0` |

The driver writes `LIKE '%COMP%'`, and Cube reads it as its `contains` operator. The driver can stop a case-sensitive clause with a message, or write another form. `case-sensitive: false` gives the truth (`edge/contains_ignore_case`). The scan can stop native `LIKE`. 14 shapes show it: `edge/like_3`, `edge/like_4`, `follow/case*`.

### B3: a native rolling window passes the scan with a function in the filter

`docs/query-compilation.md` says that the scan stops "each other use of the time column, such as `IN` or a function". It does not stop `DATE_TRUNC` on the left of a bound, or interval arithmetic in the literal. Cube then computes the whole month, and the filter has no effect.

```sql
SELECT DATE_TRUNC('month', created_at), MEASURE(revenue_mtd) FROM orders
WHERE DATE_TRUNC('day', created_at) >= '2025-03-15' AND created_at < '2025-05-01' GROUP BY 1
```

Output for March: `27121`. Truth with the filter: `15779`. `created_at >= TIMESTAMP '2025-03-01 00:00:00' + INTERVAL '14 day'` gives the same. The README has the general entry "Native SQL in a shape that the scan does not read", but this shape contradicts the sentence above, and the scan already reads `DATE_TRUNC`. These other forms stop as they must: `CAST`, `IN`, `EXTRACT`, a quoted column, a table alias, `TO_TIMESTAMP`, comments and new lines between tokens. 4 shapes show it: `native/rolling_day_trunc_in`, `follow/rolling_native/trunc_day_left`, `trunc_hour_left`, `interval_literal`.

### B4: wrong numbers with a report time zone that is not UTC

`settings_grid.py` ran the same shapes in `America/New_York`, `Asia/Kathmandu`, `Europe/Berlin` and `Pacific/Apia`. The check `mb.report_timezone` uses Tokyo only, which has a whole hour offset and no clock change, and it does not try these shapes. Each part has the same output on the dialect and on stock Cube. A bucket with no such filter gives the truth, and two bounds on one column give the truth.

**B4a. One bound on a time is read as UTC.** `docs/query-compilation.md` says that Cube reads each time literal in the report zone. For one bound it does not. The output does not change with the zone.

| Zone | Query | Output | Truth | Metabase on Postgres, `timestamptz` |
| --- | --- | --- | --- | --- |
| `America/New_York` | `orders.count`, `created_at >= 2025-06-15T11:00:00` | `2684` | `2682` | `2682` |
| `Asia/Kathmandu` | the same | `2684` | `2687` | `2687` |

`filter one date`, such as `>= 2025-03-01`, is wrong in the same way. Postgres gets `timestamp with time zone '2025-06-15 11:00:00.000 -04:00'`, and the driver sends `TIMESTAMP '2025-06-15 11:00:00'`. The driver knows the zone, so it can convert the literal or stop the query.

**B4b. A to-date rolling window adds months together.** This is a defect of Cube: its REST API gives the same numbers. The driver can stop a rolling window when the report zone is not UTC.

| Zone | Query | Output | Truth |
| --- | --- | --- | --- |
| `America/New_York` | `revenue_mtd` by month, March and April 2025 | `27166`, `54366` | `27079`, `27374` |
| `Asia/Kathmandu` | the same | `54323`, `27574` | `26953`, `27444` |

**B4c. Hour of day is wrong.** The driver writes `DATEDIFF('hour', DATE_TRUNC('day', x), x)`, which counts boundaries. In Kathmandu each row is one hour too high: output `[1, 217]`, truth `[0, 217]`. In a zone with a clock change, the day of the change moves rows, and a 25th row, hour 24, appears: New York output `[1, 219]`, truth `[1, 220]`. A filter on hour of day has the same defect. The driver wrote this form, so it can change it or stop it.

## Major

### M1: month to date by a quarter is the total of the quarter

`revenue_mtd` by quarter gives `80177` and `81673`. The month to date at the end of each quarter is `27121` and `27262`. The window is shorter than the bucket, so the truth depends on what a person means. So I did not call this a blocker. The driver can stop it, because it knows the window and the bucket. **Decision for the owner.**

### M2: week of year differs from Metabase

The driver defines week 1 as the days from 1 January to the first start of a week, in `week-of-year-from`. Metabase core uses `ceil(day-of-year(week(x)) / 7)` for this unit, and it gives another number on each week. For the week of 2025-01-05 with Sunday as first day, Cube gives `[2, 98]` and Metabase on Postgres with the same data gives `[1, 98]`. Six of the 7 values of `start-of-week` differ on Cube. Wednesday agrees, because 1 January 2025 is a Wednesday. Postgres agrees with this truth on all 21 checks in `settings.log`.

The check `mb.bucket.week-of-year` compares with `toWeek(x, 0) + 1`, so it cannot see this. Each group holds the right rows, except the first partial week, and the label moves by one. So I did not call this a blocker. On a strict reading of the definition it is one. **Decision for the owner.**

### M3: a `Date` column moves to the month before, west of UTC

With `America/New_York`, `typed_events.count` by `day@month` gives `2025-02-01: 23`, `2025-03-01: 744`, `2025-04-01: 233`. The truth is `743` and `257`, with no February. Cube converts a `Date` to the zone as if it was a time at midnight UTC. Cube does not show the type of a column, so the driver cannot stop this for one column. The README section "Known wrong numbers" does not have it, and it must.

### M4: three stock entries of "Known wrong numbers" can stop

The README says that the driver cannot stop these. See the table below. They apply only with no dialect, and each fix has a cost, so I did not call them blockers. On a strict reading of the definition they are. **Decision for the owner.**

## Minor

- **m1.** Week by the first day Sunday with `not (a or b)` fails with a raw message: `week_from_sunday doesn't look like datepart name in dateTrunc`. No number is wrong. Repro: `core/min_amount/week/not_group`.
- **m2.** The README says that native `COUNT(*)` on no rows gives `NULL`. It does so only if a rollup answers. `orders` gives `NULL`, and `typed_events` gives `0`.
- **m3.** The README says that native `SELECT *` gives each row once for each value of a switch. On `orders` of the demo it fails with `Cube needs a date range`, because the star includes a rolling measure. The message does not help with `SELECT *`.
- **m4.** The README and `docs/install.md` do not tell that `MB_PLUGINS_DIR` on the host is a mount in a container. A person with Docker must find this.
- **m5.** A dry run of the release continues to `publish` after a failure of conformance, by design. So `publish: success` alone does not show a green gate, and the run of 2026-10-30 (`41072905614`) has this result with a red conformance. The release job runs conformance with the dialect only. ## PR 3: ClickHouse 26.10.3 and `measure.rolling.unbounded_one_bucket`

**Cause: ClickHouse 26.10 accepts a join with only an inequality, so the error that the check expects no longer comes.** It is not a wrong number.

The check expects the message `for more than one bucket`. The driver writes that message when ClickHouse says `Cannot determine join keys in JOIN ON expression`. Cube writes `LEFT JOIN cte_0 ON rolling_source.m <= time_series.date_to`. The CI log shows: `the error has no 'for more than one bucket': `, with an empty error, on both variants, and it is the only failure of that run (732/761 and 728/761).

| Same SQL, direct | Result |
| --- | --- |
| ClickHouse 26.8.36 | `Code: 403. Cannot determine join keys in JOIN ON expression lessOrEquals(...)` |
| ClickHouse 26.10.3 | `1679`, `2113`. Truth: `1679`, `2113`. |

26.10.3 gives the same with `join_algorithm='hash'`, `enable_analyzer=0`, `allow_general_join_planning=0` and `query_plan_use_new_logical_join_step=0`, so no default setting that I tried explains it. I did not find the commit in ClickHouse. Through the driver on Metabase 0.65 with 26.10.3 (`dev/review/pr3.py`), `cumulative_count` is equal to ClickHouse for 1, 2 and 6 months, 4 days, and 2 months with a status. Months after the last row give the running total `5000`, which is right.

What PR 3 needs, in `conformance/` and the docs, which this review does not change: the check must accept the truth on a ClickHouse that runs the join. `measure.rolling.unbounded` can leave `blocked` on that version, and the driver must keep the message for older versions. The reason in `features.yaml` and the limit in `docs/query-compilation.md` say "ClickHouse 26.8". The diff of PR 3 still has Metabase `v0.64.3`, so it needs a rebase. I tried six shapes on 26.10.3, not the grid.

## Secrets and permissions

None found. Outputs: `results/security.log`, `results/secret-logs.log`. `FAIL` lines: none.

- **Per-person data on `cube-secure`:** two people get their own rows through `/api/dataset`, native SQL, a stage, a saved question, CSV, pivot with a total, MCP `execute_query`, `execute_sql` and `run_saved_question`, field search and stored values. 60 parallel queries do not mix.
- **Around the rule:** `__user`, `SET user`, a cross join, `information_schema` and `pg_catalog` show no other person. An unknown person gets an error, and a public link shows no rows. A hidden cube stops with dev mode off.
- **Metabase permissions:** with no query access, the query builder, native SQL and both MCP tools stop. With the query builder only, native SQL and `execute_sql` stop.
- **Secrets:** the API and MCP responses have no secret. A wrong password, a wrong REST host and a wrong API secret give clear messages. The Metabase and Cube logs have no secret. The log of `cube-secure` has one JWT, from the request with the wrong secret. `docs/security.md` documents this.
